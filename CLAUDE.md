## Corpus conventions
- Benefuture reads outputs only: beliefs and preferences are not directly accessible, so definitions, enforcement and alignment are stated over outputs.
- Understanding is shared, not moved: teaching raises the learner and leaves the teacher's level intact. Never model U as a fixed stock transferred between beings.
- The self is causal, over the long-term window (`Ha_lt`); the recognised self is a cognitive artefact kept in articles only, never measured. Neither self confers any claim over self-things beyond established relations (contracts, law, causal distribution). Property is not inherited; causal and ideological inheritance are.
- Articles spell out Benefuture's own abbreviations and symbols (understanding, not U; metric model, not MM). Common parlance (AI, GDP, DNA) and names (M-Pesa, PNAS, author initials) stay as they are. Symbols belong in the pseudocode and Lean.
- Core article format: a minimal definition (following its pseudocode line's order where one exists, key terms linked up top), pithy aspects, pithy examples; exploration belongs in the discussion; every reference carries a link. Checking a citation (author, 2026-11-06) means finding the work and skimming its content (at least the abstract or description, `tools/wiki/fetch_abstracts.py`) to confirm it supports the sentence or topic it is cited for, not only that the work exists and the metadata match. Definitions and aspects restate the author; examples and discussion may be AI-written, and the disclaimer says which.
- Formal links (author, 2026-11-08): core articles carry a Formal reference section (before See also or the disclaimer) linking, on GitHub, the Lean theorems and reference functions for their core rules, each named by its ID and file (never a line number); simulation results go under Discussion (an In simulation subsection) in plain words with links; the disclaimer says these are AI-written. `python3 tools/check_article_refs.py` checks every linked name exists. Wiki sync still waits for the author's review of the diff.
- Coherence critiques are independent of comparative ones and are welcome.

## Verification
- Toolchains: `tools/setup/toolchains.sh` installs Julia and Lean (idempotent; binaries in `~/.local/bin`). If they are missing, run it before verifying.
- Lean: `lake exe cache get` once per container, then `lake build`. Julia: `julia --project=sim -e 'using Pkg; Pkg.test()'`.
- CI is the gate: after pushing, check the "Lean Action CI" and "Julia Sim CI" runs for the head commit. A red run is diagnosed from its job log before any further edit.
- CI tiers (author): every code push runs the fast tier (`BF_TIER=fast`: rule, unit and probe files, minutes); the full suite runs nightly on `main` and on demand (workflow_dispatch, tier `full`); docs-only pushes run nothing and a newer push cancels the run it supersedes. Probes check each mechanism; the full suite checks interactions, so a red nightly blocks feature work until fixed, and a change to the simulation or the Lean rules runs the full suite locally (on Linux where platform matters) before pushing. Every mechanism has a probe; one covered only by heavy tests is a gap to close.
- The Lean analogue of the dual suites: acceptance theorems state what must hold; counterexample theorems (e.g. `survivor_floor_rises_on_removal`) state what must fail.
- Simulation (`sim/`, Julia package `BenefutureSim`): each increment starts with acceptance tests against `spec/vectors/` and an adversarial suite, run red before implementing.
- Red tests assert the outcome, not the feature (author; `docs/CODING_STYLE.md` §3): the failing baseline shows the undesired outcome on the current code (the stall, the wrong total), never only that a function or field is missing.
- Significance testing of simulation claims (author): each test states its hypothesis, direction, metric and the smallest effect that matters before measuring; arms run on the same seeds (paired, common random numbers); seeds are added by precision (`seeds_until_stable`), not fixed at a habit, and the count is reported; an effect counts only if it beats z combined standard errors (Student-t inflated), the rule Benefuture itself uses (`select_candidate_ref`), z = 2 by default and 3 (or a replication on fresh seeds) for claims entering README or BACKPROPAGATION. Four kinds of claim, each with its test (`sim/src/methods.jl`: `paired_effect`, `equivalent`, `proportion_interval`): structural (identities, conservation, rule properties) hold in every seed; effects by the significance rule; no-effect claims by equivalence within a stated margin, never by mere non-significance, with the margin shown detectable; regimes (stalls, qualification) as a proportion with its interval over enough seeds, never 'k of 3'. Only distributional claims are portable across platforms (floating point moves single seeds).
- Progressive degradation, loudly (author): where a mechanism can fail in the simulation (a model, a measurement, a currency, a rule's input), a coarser one substitutes for it during the outage, and so on down; each substitution is recorded loudly (a `degraded` entry in the run's trace with step, mechanism, substitute and reason, and a warning once per kind), never silent and never stalling the run. Silent failures cannot be fixed.
- Mechanism probes first (author): a new mechanism is shown working in a probe before it enters the iterated ecosystem (rungs, batteries): the smallest world that exercises it alone (a few agents and beings, tens of steps, one to three seeds, seconds to run), with its acceptance and counterexample cases, in `sim/test/probe_tests.jl`, runnable alone (`julia --project=sim sim/test/probes.jl`). Only a mechanism whose probe is green is wired into the full worlds; full runs and batteries then measure interactions, not whether it works.
- Rules live once, in the Lean reference (`BenefutureReference`), exported through `BenefutureReference/Export.lean`; Julia calls them by `ccall` and holds only the world model and input guards. Loading `BenefutureSim` rebuilds the shared library only when the hash of the Lean sources changes. A new rule is a Lean reference function plus one export and one thin Julia wrapper, never a Julia reimplementation.
- `BenefutureReference` and `Main.lean` must not import Mathlib or `Benefuture.*` (CI guard).
- Lean ignores borrow annotations on `@[export]`: exported functions consume every argument. Arrays returned to Julia are read through `lean_floats` (`sim/src/domains.jl`), which takes a reference before each read.
- The simulation's outcome is a system of rules ready for implementation: the end state models the Lean objects one to one, keeps no toy assumptions, and absorbs messy reality. Toy worlds are stages that name the objects they approximate and the toy assumptions they still make, and graduate (`docs/PLAN.md`).
- Every gate value, modifier and coefficient a rule uses is a threshold to be governed later: list it in `sim/README.md` (Governed thresholds) with its default and source. Properties of the world (skills, noise, contract terms) are not thresholds; they go under Noise or the world's parameters.
- Every step that can go wrong in reality carries a noise parameter, on its own random stream, with a range to explore (`sim/README.md`, Noise).
- World parameters, noise distributions and their ranges are adapted to realistic source data as far as possible, with the source and its confidence recorded (`docs/CALIBRATION.md`, author note 8.63); governed thresholds keep governed defaults, citing institutional analogues where they exist. Behaviour is never assumed ideal: people take advice partly or not at all, at measured rates. Adapt a figure to the scale of what it means (the simulation's unit, step and population), and only where it would hold in a Benefuture society: invariant figures (human or physical nature) carry over; figures produced by today's institutions (vigilance, deception, audit and reporting rates, R&D share, delegation behaviour) are a status-quo baseline or a sweep, never a default, since in Benefuture they should emerge from its incentives.
- G is not a global chooser (author ruling 8.50): every entity runs its own messy approximation of G on its own noisy view of reality; many act each step, concurrently. A single global G is a limiting case for tests.
- Success is the Goal's whole pattern (L74), not the floor alone: floors and medians of understanding and happiness, the peak of understanding (none falling), and harm's peak (the deepest single-being drop). Tests and batteries judge by it (`success_pattern`, `sim/src/analysis.jl`).
- Nothing is perfect (author ruling 8.33): world defaults are mildly imperfect (the low end of each noise range); exact models, people or processes appear only as limiting cases in tests. Apply Benefuture's logic to the work: truth levels never reach 1, so claims carry their confidence and assumptions.

## Working
- Parsimony. Before adding a mechanism, establish that no existing one handles the case: an outcome recorded with its measured outputs mints or destroys currency, causal distribution shares it, laws and contracts learn from it. The simulation should need nothing beyond the Lean and the pseudocode; where it does, the extra is named in `sim/README.md` (Parsimony audit) as introduced, with the reason, and is a candidate for removal. Actively look for introduced mechanisms that native ones already cover, and for redundancy in the corpus (proposals go to `docs/BACKPROPAGATION.md`).
- Gaming. For every mechanism added, ask how it can be gamed or complied with maliciously before building it (a payment for braking rewards near misses), and record the answer with it; plausible exploits become M6 tests.
- Duties stay minimal, but are real (author ruling 8.46): some contribution and participation is a duty (voting above a threshold, care not to harm others in obvious ways), and the line where a duty becomes a recommendation is a governed threshold. Freedom pushes back on duties and laws: they protect only against outcomes beyond the freedom harm boundary. Never model duties as a separate rule set binding agents; they are contracts and communicated laws, assessed through ordinary outcomes.
- Horizons (author ruling 8.64): the economy handles 10 years, governance 20; batteries sometimes run a century of both together with catastrophes and breakthroughs at roughly realistic frequencies.
- Compute (author): the overnight batteries run on the local machine; wide and deep batteries (sensitivity maps, z = 3 replications, population scale, century bulk) run continuously as needed, sharded on free GitHub runners (`.github/workflows/battery.yml`), and the full test suite runs sharded. Compute-light work (E4 replay) stays local.
- Failure-boundary batteries (`sim/battery/`) run in the background continuously, like threshold perturbation: never wait on them. When one finishes, record its results (tagged with the commit they ran on) and start a fresh run on the latest build if the simulation, the Lean reference or the battery itself changed since (seeds are fixed, so an unchanged build repeats its results); work from their data to improve the framework. Launch them with `tools/battery/run.sh`; the project hooks (`.claude/settings.json`, `tools/battery/hook.sh`) report their state each prompt, relaunch any a container restart killed (evaluations are cached on disk per code hash, so a relaunch resumes), and block the stop once when one finishes so its results get recorded. Batteries inform strategy and never block progress: keep working on the plan while they run, and check their state yourself rather than holding a waiter open.
- Predict, measure, adapt (author ruling 8.134): every measurement and the decision it feeds runs on this loop. State the prediction, its ETA and its confidence before acting; judge at the ETA, with grace for the ETA, the confidence and the prediction itself; then adapt. This applies to Benefuture's rules in the simulation (governance candidates resolve against their own predicted trajectory and horizon) and to the work itself (state what a change should do, by when, how sure, then check).
- Orchestration (author, 2026-11-13): the lead session's tokens are costly. It orchestrates: sets tasks with their predictions and acceptance checks, reviews results, records rulings, coordinates. Implementation, test runs, traces and sweeps go to Sonnet subagents and to the remote/local agents (`COORDINATION.md`); the lead reads their summaries, not their logs.
- Next steps (author, 2026-11-08): an update that names what is next either starts on it in the same turn or arms a two-minute self-reminder (`send_later`) to continue; never end on "next is" with nothing armed.
- When instructed to make progress and blocked on something that needs the author, first check the author's past rulings (`docs/BACKPROPAGATION.md`) and their general spirit for an answer; if they settle it, proceed and record the reasoning. Otherwise keep it as an open question and continue every other task; stop to ask only when all that remains are open questions and all plan progress is blocked (author, 2026-11-07). Not when asked for one specific task.

## Records
- `README.md` is short (author, 2026-11-06): what Benefuture is and could make possible in the author's framing (confident about the design: a chosen telos, reasons from established science and philosophy, time-tested mechanisms, its strength in their synthesis), how its mechanisms connect, and one status table (proved, simulated, real data, in progress, open). The detail lives in `docs/CLAIMS.md` (every claim in plain words: proved in Lean, true by construction, or demonstrated in simulation, with links, hypotheses and toy assumptions; never more), `docs/OPEN_PROBLEMS.md` and `docs/BUILD.md`. Caution sits beside each claim, never as the frame of the whole. Links name the theorem (its ID) and its file, never a line number; `python3 tools/check_readme_claims.py` checks every named theorem exists. Update it with each increment; regenerate `docs/THEOREM_INDEX.md` with `python3 tools/theorem_index.py` when theorems change.
- README each round (author): every round of work that changes what is proved, simulated or open ends with `README.md` brought up to date in the same push: the status table and counts in `README.md`, the claims record in `docs/CLAIMS.md`, and the open problems in `docs/OPEN_PROBLEMS.md`. A claim that no longer holds is restated or marked unsupported there, never left standing. The README states current status only; the history of issues found and fixed goes to `docs/BACKPROPAGATION.md`, `docs/SPEC_DIVERGENCES.md` and `docs/CLAIMS.md`, never the README (author, 2026-11-06). The README speaks to formal and informal readers alike: wins stated with their preconditions, failures with their conditions, what already limits them and their tracked fix, since readers overindex on failures and read humility as incompetence.
- Documentation sweep (author, 2026-11-08): after every major update, and at least fortnightly, consolidate the records so they agree: `README.md`, `docs/CLAIMS.md`, `docs/OPEN_PROBLEMS.md`, `docs/BACKPROPAGATION.md` (statuses of rulings and proposals), `docs/SPEC_DIVERGENCES.md`, `docs/SIM_CONJECTURES.md`, `docs/PLAN.md` Part 2 and `sim/README.md`. Stale claims are restated or marked unsupported, contradictions resolved to the current evidence, done items closed; every open problem names the friction the framework already builds against it before what remains open (author, 2026-11-08); run the checkers (`tools/check_readme_claims.py`, `tools/check_article_refs.py`).
- Author clarifications, and strong requirements or proposals the work surfaces, go to `docs/BACKPROPAGATION.md` as they arise, with candidate homes in the sources; withdrawn proposals are marked, not deleted.
- Process changes the author asks for go into this file and `docs/PLAN.md` in the same commit.
